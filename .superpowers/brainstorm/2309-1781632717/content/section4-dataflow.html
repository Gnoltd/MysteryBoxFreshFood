Section 4 — Data Flow & Error Handling

Two critical journeys: Purchase flow · QR pickup flow

Journey 1 — Customer Purchases a Box

1
Customer clicks "Buy" on ListingDetailPage
→ calls stripe.createCheckoutSession(listingId, qty) service fn
2
Cloud Fn: createCheckoutSession
Checks quantityRemaining ≥ qty (transaction) · Creates Stripe Checkout session · Writes orders/{id} with status "pending" + stripeSessionId · Returns session URL
3
Browser redirects to Stripe Checkout
Customer enters test card (4242 4242 4242 4242) · Stripe processes payment
4
Cloud Fn: stripeWebhook fires
Verifies Stripe signature · Finds order by stripeSessionId · Sets status → "paid" · Decrements quantityRemaining via transaction
5
Stripe redirects to /checkout/success
Page polls order status (onSnapshot) until "paid" · Navigates to /orders/:id · QR code displayed

Journey 2 — Vendor Scans QR at Pickup

1
Vendor opens /vendor/scan · html5-qrcode activates device camera
2
Customer shows QR code from /orders/:id · Vendor scans it
3
QR decoded = UUID (order's qrCode field)
Firestore query: find order where qrCode == uuid AND vendorId == currentUser.uid AND status == "paid"
4
Order found → update status to "picked_up" · Show confirmation screen
If not found or wrong vendor → show error: "Invalid or already used QR code"

Error Handling Strategy

Out of stock at checkout

createCheckoutSession checks qty before creating session · Returns error → client shows "Sold out" toast, disables button

Stripe payment fails

Stripe redirects to /checkout/cancel · Pending order stays in Firestore (cleaned up by a scheduled function or TTL)

Invalid / used QR code

Query returns nothing or wrong vendor → inline error in scanner UI, camera stays open for retry

Auth / Firestore errors

Toast notifications via a shared useToast hook · Form validation errors shown inline
